Loss less join decomposition --- we have 2 rel schema r1 and r2 s.t
for all attributes in r1 and r2 , we have r1 u r2 -> r1 and r1 u r2 -> r2 holding good .
dependency preservation occurs herein




Existence dependencies --- there is a rel schema r where for all
attributes in r , the functional dependency is x -> y s.t if operationally y is deleted ,
so is x. y is dominant entity , x is subordinate entity . dependency preservation occurs herein



Types of functional dependencies ---
1 . full functional --- all non key attributes are fully dependent on key attribute
2 . partial functional dependency ---- some non key attributes are dependent on key attribute and remaining non key attributes
are dependent on key attribute and on some other non key attributes
3 .transitive dependency--- attributes in key col of 1 rel correspond to the key attributes in col of another rel
4 . multi valued dependency --- in 4NF
5 .join dependency --- in 5NF


The removal of redundancy from tables or rels is normalization. While 1nf has redundant data
that is removed to some extent in 2nf . still higher nf is BCNF that mentions super key values .
all rels in 3NF are in BCNF but the reverse is not always true . there’s a rel r where for all functional dependencies f on r , can find a <- r ,b <- r s.t a ->b is a trivial
dependency in f+ ,s.t at least one of following is true :
a -> b is trivial dependency in r
a is a super key to r

Still higher nf is 3NF that mentions candidate key values , transitive dependencies .
there’s a rel r where for all functional dependencies f on r , can find a <- r ,b <- r s.t a -> b is a trivial dependency in f+ ,
s.t at least one of following is true :
a ->b is trivial dependency in r ,
a is a super key to r,
can find an extraneous attribute in [b-a], that is contained in a candidate key for r
4NF mentions multi valued dependencies
5NF mentions join dependencies


A transaction is a unit of program execution that accesses and or possibly updates various data items . acid properties of a transaction are :
1 atomicity --- either transaction executes in entirety or none executes at all
2 consistency --- state of database remains same both before and after transaction despite system changes
3 isolation --- despite concurrent execution of transactions , each transaction proceeds independent of others despite
system changes
4 durability --- any modifications made to database as a result of transaction persist even if there are system changes

Examples – there’s a schedule involving 2 accounts a and b, initial values in a and b are$1000 and $2000 .
a transaction occurs that transfers $ 50 from a to b , as a result , final values in a and b become $ 950 and $ 2050 ,
clearly a consistent state, as sum a+b is preserved both before and after transaction .
thereafter we suppose that a system failure occurs after write –a committed but before write –b committed ,
so final values in a and b become $ 950 and $2000 clearly an inconsistent state as sum a+b is no longer
preserved both before and after transaction . even if system failure did not occurs and transaction proceeded to completion,
this inconsistent state would not have been visible except during occurrence of transaction.
This reflects again atomicity . isolation is preserved . durability is preserved through recovery mgmt. component of transactions
